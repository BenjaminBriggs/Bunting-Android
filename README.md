# bunting-sdk-android

Kotlin client SDK for [Bunting](../docs/README.md) feature flags — the Android counterpart to `bunting-sdk-swift`. Fetches a signed `config.json`, verifies a detached RS256 JWS offline, caches it, and evaluates flags locally.

> [!TIP]
> Full documentation for the dashboard, SDK integration, and self-hosting lives at **[benjaminbriggs.github.io/Bunting-Documentation](https://benjaminbriggs.github.io/Bunting-Documentation/)**.

## Modules

| Module | Type | Contents |
|---|---|---|
| `:bunting-verify` | pure JVM | Detached-JWS (RS256) signature verification (mirrors Swift `BuntingVerify`) |
| `:bunting` | pure JVM | Models, evaluation engine, config store, identity, overrides, and the public `Bunting`/`BuntingClient` facade (mirrors Swift `Bunting`) |
| `:bunting-cli` | pure JVM | CLI that fetches/verifies/decodes a config from a bootstrap JSON document |
| `:bunting-android` | Android library (minSdk 26) | `Bunting.configure(context, …)`, device context derivation, assets bootstrap/seed loading, foreground auto-refresh |
| `:bunting-debug` | Android library (Compose) | `BuntingInfoScreen` (read-only inspector) and `BuntingDebugScreen` (override editing, environment switch) |
| `bunting-codegen-gradle/` | included build | Gradle plugin `io.github.benjaminbriggs.bunting.codegen` generating strongly-typed accessors from a seed config |
| `:example` | Android app | Compose demo wiring all of the above together |

The pure-JVM core keeps unit tests, the conformance runner, and the CLI headless (no emulator).

## Installation

The libraries are on Maven Central under the group `io.github.benjaminbriggs` (artifact IDs are the module names); the codegen plugin is on the Gradle Plugin Portal. The Kotlin packages stay `com.bunting.*`.

```kotlin
// settings.gradle.kts
pluginManagement {
    repositories {
        gradlePluginPortal()
        google()
        mavenCentral()
    }
}
dependencyResolutionManagement {
    repositories {
        google()
        mavenCentral()
    }
}
```

```kotlin
// app/build.gradle.kts
plugins {
    id("com.android.application")
    id("org.jetbrains.kotlin.android")
    id("io.github.benjaminbriggs.bunting.codegen") version "1.0.0"   // optional: typed accessors
}

dependencies {
    implementation("io.github.benjaminbriggs:bunting-android:1.0.0")   // brings in :bunting and :bunting-verify
    implementation("io.github.benjaminbriggs:bunting-debug:1.0.0")     // optional: Compose Info/Debug screens
}
```

A pure-JVM project (no Android) depends on `io.github.benjaminbriggs:bunting:1.0.0` instead. `bunting-cli` is not on Maven; each GitHub release attaches `bunting-cli-<version>.zip` (run `bin/bunting-cli`).

## Quickstart

Add `bunting_config.json` (bootstrap: endpoint, public keys, fetch policy — generated by the admin) and optionally `BuntingConfig.json` (a bundled seed config) to your app's `assets/`, then:

```kotlin
// Application.onCreate
Bunting.configure(this, BuntingEnvironment.PRODUCTION)
```

Read flags synchronously anywhere:

```kotlin
Bunting.bool("store/use_new_paywall_design", default = false)
Bunting.state          // StateFlow<BuntingState> for Compose/observability
Bunting.instance.refresh()   // suspend; also runs automatically on foreground
```

### Typed accessors (codegen)

Apply the plugin and point it at your seed config:

```kotlin
plugins { id("io.github.benjaminbriggs.bunting.codegen") version "1.0.0" }

buntingCodegen {
    packageName = "com.example.app.flags"   // default: com.bunting.generated
    // seedConfig defaults to src/main/assets/BuntingConfig.json
}
```

`store/use_new_paywall_design` then reads as `Bunting.store.useNewPaywallDesign` (Swift: `Bunting.shared.store.useNewPaywallDesign`). Accessors read through the `Bunting.bool(...)`-style facade, so before `Bunting.configure` runs they return the seed's development default instead of throwing.

Defaults come from the development environment and are read by each flag's declared `type`, never by JSON shape: `bool` is a JSON boolean, `int` a JSON number with no fractional part within ±(2^53 - 1) (`2.0` counts), `double` any finite JSON number, `string` the string verbatim, `date` an ISO-8601 UTC instant ending in `Z` with up to three fraction digits that names a real calendar moment (years 0001 to 9999; offsets, `24:00`, leap seconds and dates like `02-30` are invalid), and `json` a JSON-encoded string. A flag the SDK would skip when decoding (unknown type, a missing environment, a default in any environment that isn't valid for its type, or `variants` that isn't an array) gets no accessor and a build warning. Flag keys that are Kotlin keywords are backticked and leading digits are prefixed with `_` (`2fa_enabled` becomes `Bunting._2faEnabled`).

Codegen never fails the build over seed content: a missing or invalid seed generates a fallback file and string-based access keeps working. The one exception is two flags whose keys map to the same accessor (for example `dark_mode` and `dark-mode`): the build fails and names both keys, because one accessor would otherwise silently shadow the other.

### Fetching the latest config (Swift `FetchConfigPlugin` equivalent)

The plugin also registers `fetchBuntingConfig`: it reads the module's bootstrap (`assets/bunting_config.json`), downloads `config.json` from the endpoint, verifies the detached RS256 JWS offline, checks the payload is a usable seed (it rejects what the SDK's decoder rejects at header level: invalid JSON, `schema_version` other than 1, a missing `config_version`, `published_at` that isn't a UTC instant, a missing `app_identifier`, and `flags`, `tests` or `rollouts` that aren't objects; flags codegen will skip are reported as warnings), and only then overwrites the seed (`assets/BuntingConfig.json`), refreshing both the codegen input and the config bundled with the app. Run it from Android Studio's **Gradle tool window → (module) → Tasks → bunting → fetchBuntingConfig**, or:

```bash
./gradlew :app:fetchBuntingConfig
```

On any fetch, verification, or validation failure the task fails without touching the existing seed. The seed is saved without its signature on purpose: it ships inside the signed app, and the SDK treats it as unverified.

### Debug UI

```kotlin
BuntingInfoScreen()    // read-only: searchable flag list, details sheet (incl. copyable config fingerprint), pull-to-refresh
BuntingDebugScreen()   // adds override editing, clear-all, reset identity, environment switch
```

## How configs are decoded and evaluated

The SDK decodes `config.json` by the v1 wire contract. The admin's `src/lib/artifact-decoder.ts` is the reference, and the conformance bundle's `decoding` set pins it.

- **One bad entry never rejects the artifact.** A flag with an unknown type, a missing environment, a default that doesn't match its type, or a `variants` that isn't an array is skipped, so its accessors return the call-site default. A variant with an unknown type, or a missing or mistyped value or reference, becomes a placeholder that never matches; one without an integer `order` is dropped. A condition with an unknown type or operator, or `values` that aren't all strings, never matches. A malformed test or rollout is dropped, and variants referencing it never match. Unknown keys are ignored. Everything skipped is logged through `java.util.logging` (`com.bunting.storage.ConfigStore`).
- **Only the header is strict.** Invalid JSON, a `schema_version` other than 1, a missing `config_version` or `app_identifier`, a `published_at` that isn't an ISO-8601 UTC instant, or a `flags`/`tests`/`rollouts` container that isn't an object rejects the artifact. A rejected fetch fires `didCompleteFetch(false, error)`, keeps the active config (cache or seed), and waits for the normal fetch schedule before trying again.
- **Values decode by the flag's declared type, never by their JSON shape.** `bool` is a JSON boolean; `int` a number with no fractional part (`2.0` is 2); `double` any finite number (`3` is 3.0); `string` any string, verbatim; `date` an ISO-8601 UTC instant on a real calendar date with 0 to 3 fraction digits (`2026-07-02T10:00:04Z`, `2026-07-02T10:00:04.796Z`); `json` a string holding JSON text, verbatim (`"42"` is valid, a raw object is not). Overrides convert by the declared type too.
- **A/B tests.** A test variant serves a value only when the test's preconditions pass, the user buckets into a group, and that group has a value in the variant. Otherwise, including for users in the remainder when the groups sum to under 100, evaluation moves on to the next variant and then the default. The config fingerprint records the same path.

`ArtifactDecoder.decode(text)` returns the decoded `BuntingConfiguration` together with every `DecodeIssue`; `BuntingConfiguration.serializer()` decodes by the same rules.

## Build & test

**Android Studio:** open the repo root (`bunting-sdk-android/`), not `example/` — the example is a module of this multi-module build (unlike the Swift repo's standalone Xcode project) and has no Gradle build of its own. After sync, pick the `example` run configuration.

```bash
./gradlew build        # compile + test all modules, incl. the codegen plugin's own build
./gradlew :bunting:test --tests 'com.bunting.conformance.*'   # conformance gate
./gradlew :example:assembleDebug                              # demo app
```

## Releasing

Pushing a tag `v<VERSION_NAME>` runs `.github/workflows/release.yml`: it re-runs CI, uploads the libraries to the Maven Central Portal, and creates a GitHub release with the CLI zip. The Central deployment is then released by hand in the portal. Only after the libraries are on Maven Central is the codegen plugin published, by running the manual **Publish codegen plugin** workflow (`.github/workflows/publish-plugin.yml`), which refuses to run until they are. The version lives in one place, `VERSION_NAME` in `gradle.properties`. One-time account, key, and secret setup is in [docs/releasing.md](docs/releasing.md). `./gradlew publishToMavenLocal` and `./gradlew -p bunting-codegen-gradle publishToMavenLocal` work without any keys.

## Conformance

The vendored bundle under `bunting/src/test/resources/conformance/` is a copy of `bunting-admin/conformance/`. Re-sync with:
```bash
cp -R ../bunting-admin/conformance/. bunting/src/test/resources/conformance/
```

## Documented divergences from the Swift SDK

- **Identity** is a per-install UUID persisted in app storage; there is no iCloud-Keychain equivalent, so identity does not survive reinstall or sync across devices.
- **Storage** uses a file-backed `KeyValueStore` in app-private `filesDir` (atomic temp-then-rename writes), not DataStore — same guarantees for these tiny single-process maps, no extra dependency.
- **Threading**: flag accessors are lock-free reads of an atomic snapshot and are safe from any thread (Swift's are `@MainActor`).
- **Events**: `BuntingClient.eventsListener` is a plain nullable reference, not weak — clear it when the listener's lifetime ends.
- **Debug UI** enumerates flags from the loaded configuration at runtime instead of a generated `allFlags` list.
- **Codegen** emits namespace classes (`StoreFlags`) via string templates; `int` flags surface as `Long`, `date` as `java.time.Instant`, `json` as `ByteArray?`.
